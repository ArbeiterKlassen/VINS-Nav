# VINS-Nav 性能攻坚：伪双目 4 倍提速、真值验证下的误差溯源，与建图质量的诚实对比

> 接续 [EGO-Planner 集成：VIO + 建图 + 规划全栈融合](https://soyorin.work/articles/000033.html)。
> 那一篇讲的是「怎么把三套系统拼起来」，这一篇讲的是「拼起来之后，为什么它跑不好，以及我查到了什么」。

## 摘要

000033 结尾时，系统结构上完整了：VIO 出里程计、RTAB-Map 出地图、EGO-Planner 出轨迹。但它跑不好——回放一段 16 分钟的 bag，VIO 会在中途发散成 NaN，地图裂成两块，规划器无路可走。

这一轮我没有再去调参数，而是先做了三件更基础的事：**找到吞吐瓶颈并消除它**、**建立一个可信的真值基准**、**用真值量化误差到底出在哪里**。结论有些出乎意料：

- 伪双目的空洞填充占了单帧 78% 的耗时，把它从关键路径上拿掉，节点从 4.4 Hz 提升到 16.8 Hz；
- 轮式里程计积分出的真值显示，**VIO 在 95% 的时间里尺度是 0.995、RMSE 只有 2 厘米**——它并不「漂」，而是在**两个特定时段**突然报出约 2 倍的运动量；
- 建图条纹的根因不是算法，是 **RTAB-Map 的 `Grid/3D` 默认为 true 导致 2D 光线投射根本没生效**；
- 但修复条纹之后，用人工标注的户型图对比，**实时建图的结构反而不如离线建图完整**——这一点必须如实说。

文中也记录了我自己犯的两个错：一个让验证基准本身失真，一个让「修复」把结果改得更糟。

## 1. 起点：000033 留下的三个问题

000033 结束时，已知的遗留问题是三个：

1. **全栈负载下伪双目掉到 13 Hz**，VIO 拿不到足够的立体帧；
2. **长时间回放会发散**——约 500 秒后 `/ov_msckf/odomimu` 输出 NaN，经 TF 传出去变成 `TF_DENORMALIZED_QUATERNION` 警告，规划器随即停摆；
3. **地图分离**——离线建图需要用 `corr_dx=-3.2, corr_dy=-1.25` 这种手工参数把左半边的点云整体平移，才能拼成一张完整的图。

第 3 条最刺眼：一个「临时调整」的参数，说明根因没被理解。

## 2. 伪双目吞吐：从 3.5 Hz 到 24.9 Hz

### 2.1 先定位瓶颈，而不是猜

隔离实验：**只跑伪双目 + OpenVINS**，关掉 RTAB-Map 和规划器，排除 CPU 争抢。用 bag 里的真实深度图做微基准：

```
逐行前向 warp:        62.9 ms
cv2.inpaint(INPAINT_NS): 223.0 ms   ← 78% 的时间在这里
合计:                 285.9 ms  →  理论上限 3.5 Hz
```

深度图的有效像素只有 **54.8%**，将近一半是空洞，Navier-Stokes inpainting 要处理一个巨大的掩膜。而 VIO 需要约 28 Hz 的立体帧，实际只有 3.5 Hz——**跟踪长期处在饥饿状态**。

这解释了为什么 VIO 会「突然」发散：它不是慢慢漂，而是一直在低质量输入下硬撑，某个时刻撑不住了。

### 2.2 优化一：Z-buffer 分组

原来的逐行 Z-buffer 用 `np.unique` 对目标列去重：

```python
order = np.argsort(-disp)
u_dst_s = u_dst[order]
_, first = np.unique(u_dst_s, return_index=True)
```

`np.unique` 内部会对整个数组重新排序，而数组已经按视差降序排过了。改用 `np.lexsort` 一次排好（主键目标列升序、次键视差降序），再用布尔差分找分组起点：

```python
order = np.lexsort((-disp, u_dst))
u_dst_s = u_dst[order]
starts = np.empty(len(u_dst_s), dtype=bool)
starts[0] = True
starts[1:] = u_dst_s[1:] != u_dst_s[:-1]
```

输出**逐像素完全相同**（我用真实帧比对验证过），耗时 41.4 ms → 31.9 ms。

### 2.3 优化二：空洞填充策略可选

把填充从硬编码改成参数 `~fill_mode`，实测四种策略：

| `fill_mode` | 每帧耗时 | 频率 | 说明 |
|---|---|---|---|
| `morph`（默认） | 40.2 ms | 24.9 Hz | 形态学闭运算，把真实像素膨胀进空洞 |
| `none` | 32.8 ms | 30.5 Hz | 空洞保持黑色 |
| `inpaint_ds` | 49.3 ms | 20.3 Hz | 1/4 分辨率 TELEA inpaint 后上采样 |
| `inpaint_ns` | 201.5 ms | 5.0 Hz | 原始行为，保留用于对照 |

**一个反直觉的发现**：用 OpenVINS 同款 KLT（win 15、4 层金字塔）在合成立体对上测试，`none` 和 `morph` 的**立体匹配结果完全相同**——154 个特征检出、93 个匹配成功、深度中位比 1.043，两者一模一样。原因是 KLT 的初始猜测就是左图位置，局部纹理主导收敛，填充与否不影响成功的匹配。

所以「inpainting 能提升 VIO」这个说法，在合成立体这个场景下**没有得到验证**。真正的限制是：约 40% 的可检出特征根本拿不到立体匹配（对应点落在深度不连续处或空洞里）。

### 2.4 效果验证

| | 优化前 | 优化后 |
|---|---|---|
| 单帧耗时 | 285.9 ms | 40.2 ms |
| `/camera/right/image_raw` | 4.4 Hz | **16.8 Hz**（追平输入速率） |
| 900 秒回放（仅 VIO）NaN | 约 450 秒发散 | **全程 0** |

全栈负载下会降到约 13 Hz，但已经不再是唯一的限制因素。

## 3. 建立可信真值：从轮子关节角积分

### 3.1 bag 里没有现成的真值

第一反应是找 Gazebo 的里程计。bag 的 `/tf` 里确实有 `odom → base_footprint`（9819 条），但它**全程恒定在 (0, 0, -0.078)**——那是 launch 里的静态变换，不是差分驱动插件的输出。Gazebo 的真值里程计在录制时被静态发布器覆盖了。

### 3.2 换一条路：轮子关节角

bag 里还有 `base_link → wheel_left_link` / `wheel_right_link`（各 29,749 条），来自 `robot_state_publisher`，输入是 Gazebo 的 joint states。**这是真正的物理量**，可以积分成轨迹：

```
ds = (dφ_r + dφ_l) · R / 2
dθ = (dφ_r − dφ_l) · R / L
```

TurtleBot3 waffle：轮半径 R = 0.033 m，轮距 L = 0.287 m（从 Gazebo 差分驱动插件的 `wheelDiameter`/`wheelSeparation` 读出）。

### 3.3 一个代价不小的坑

第一版实现我直接用四元数取 yaw：

```python
_, _, yaw = tft.euler_from_quaternion(q)   # 错
```

结果「真值」的航向以 **20.6° 的固定步长来回横跳**，角速度在 ±41°/s 之间反复变号。一台差速轮式机器人不可能这样运动。

原因：`base_link → wheel_left_link` 的变换里含有关节原点的固定旋转 `rpy=(-1.57, 0, 0)`，直接取 yaw 得到的是两者复合后的角度，不是关节角。正确做法是先把原点旋转除掉：

```python
R_z = R_origin.T @ R_measured
theta = math.atan2(R_z[1, 0], R_z[0, 0])
```

**这个错误的代价**：我一度据此得出「机器人在静止而 VIO 飞走 3.5 米」的结论，并写进了文档。修正后重算，结论完全不同——VIO 其实非常准。**验证的基准本身也需要被验证。**

修正后的轮式里程计：角速度均值 2.3°/s、95 分位 13°/s、最大 81.8°/s，全部在物理范围内。

## 4. VIO 的真实精度画像

用修正后的轮式真值做 Umeyama 对齐（尺度 + 旋转 + 平移）：

### 4.1 大部分时间近乎精确

| 区间 | 结果 |
|------|------|
| t = 850–955 s | 局部对齐**尺度 0.9950，RMSE 0.020 m** |
| t = 252–873 s | 分段尺度 0.977 / 1.046 / 1.022 / 1.020 / 1.009 |

**2 厘米的 RMSE**——在这个尺度上，伪双目方案的精度已经接近真值本身的不确定度。000031 里那个 0.991 的尺度指标，在更长的轨迹上依然成立。

### 4.2 两个故障窗口

| 窗口 | 现象 |
|------|------|
| **t ≈ 955–975 s** | 误差从 0.07 m 涨到 **3.55 m**。轮式真值显示机器人此时在**慢速直行**（0.11 m/s、航向恒定 104°），VIO 却报出约 2 倍的运动量 |
| t ≈ 1121–1245 s | 尺度 1.12 |

关键细节：误差**涨上去就不再恢复**。t=975 之后误差稳定在 3.0–3.5 m，直到录像结束。累计路程上，VIO 走了 90.7 m 而轮子只转了 79.4 m，其中约 6.8 m 的额外路程全部来自 t=960–1000 这 40 秒。

**所以「地图分离」不是全局尺度膨胀，而是两个局部时段的位姿错误。** 这也是为什么 `corr_dx/corr_dy` 那种按空间位置整体平移的做法能「看起来管用」——它本质上是在补这两个窗口造成的错位。

### 4.3 撤回一个错误结论

基于上面那个错误的真值，我曾写下「正常运动段隐含 0.5–0.7 m/s，是物理上限的 2–3 倍，说明尺度膨胀」。这个说法**不成立**，已在 README 中撤回。VIO 的尺度是准的，问题在别处。

## 5. 深度流的两个硬事实

调参之前值得知道：

- **有效像素比例恒为 62.5%，恰好是 300/480 行**。每帧底部第 355–479 行**在每一帧都 100% 无效**——这是一个结构性的死区，不是传感器噪声，任何形态学填充都补不上。
- **最大量程被截断在 4.49 m**。

这也解释了为什么 `RangeMax=20` 是错的：它允许远超传感器能力的点参与建图。

## 6. 建图重影：根因与修复

### 6.1 条纹是怎么来的

RTAB-Map 在 Noetic 下的默认安装**链接了 OctoMap**，因此 `Grid/3D` 默认为 **true**：2D 栅格是从八叉树投影出来的，而 **2D 光线投射（`Grid/RayTracing`）只在 2D 路径下生效**。

后果是：栅格**只做命中计数**。一个错误的深度点（深度不连续处的飞点、错误的立体匹配）投出去，那一格就永久被占据，永远没有「自由空间」的证据去和它竞争。连续多帧从相近方位投出这样的点，就形成了从轨迹向外辐射的条纹。

这是占据栅格地图的标准教科书写法要用光线投射 + log-odds 的原因——**命中与未命中必须互相竞争**。

### 6.2 修复

| 参数 | 默认 | 改为 | 原因 |
|------|------|------|------|
| `Grid/3D` | true | **false** | 走 2D 路径才能启用光线投射，且更省算力 |
| `Grid/RayTracing` | false | **true** | 雕刻自由空间，擦除瞬态错误点 |
| `Grid/RangeMax` | 5.0 | **4.5** | 实测的传感器截断距离 |
| `Grid/RangeMin` | 0 | **0.2** | 丢弃近处飞点 |
| `Grid/DepthRoiRatios` | 0 0 0 0 | **0 0 0 0.26** | 裁掉每帧底部 26% 的死区 |
| `Grid/NoiseFilteringRadius` | 0.0 | **0.1** | 离群点滤除（原本是关闭的） |
| `Grid/MaxGroundHeight` | 0.0 | **0.20** | 机器人高度的地面分割 |

### 6.3 A/B 实测

同一段 400 秒回放、完全相同的输入，只改栅格参数：

| | 地图尺寸 | 障碍格 | 自由格 |
|---|---|---|---|
| 默认参数 | 264×227 | 15,035 | 6,318 |
| 新参数 | 236×215 | 4,577 | 22,855 |

视觉上：默认参数的地图布满放射状拖影和黑色噪点；新参数下条纹完全消失，自由空间被正确雕刻。

### 6.4 但是——结构不完整，这一点必须说清楚

我请人对照 Gazebo 户型做了一张人工标注图（真值），把四个版本并排对比：

| 版本 | 房屋结构 |
|------|----------|
| 人工标注（真值） | 完整：外墙、隔断、家具块、门洞 |
| **离线 `build_map.py`** | **最接近真值**——房间划分和家具都清晰可辨 |
| RTAB-Map 默认参数 | 一坨黑斑，结构几乎不可辨 |
| RTAB-Map 新参数 | 条纹消失了，**但墙体被打碎、结构残缺** |

**结论是诚实的，也是不完美的：**

- 光线投射在**消除条纹**上确实有效；
- 但它同时**抹掉了薄墙和低矮结构**，而且 4.5 m 的射线量程让地图呈现出以轨迹为圆心的圆形边界；
- 更根本的是，**实时 RTAB-Map 建图的质量明显不如离线 `build_map.py`**——后者用记录下来的位姿逐帧投影深度点、按高度区分墙面与地面，结构完整度高得多。

所以对于「要一张能用的地图」，当前的推荐是：**用离线 `build_map.py` 出图，RTAB-Map 只负责实时定位（`map→odom`）**。实时建图要追上离线质量，还需要更细的调参或换一套建图前端。

## 7. 一次失败的「修复」：ZUPT 门限

`estimator_config.yaml` 里原本是：

```yaml
try_zupt: true
zupt_chi2_multipler: 0    # set to 0 for only disp-based
```

`0` 表示**只靠视差判断**零速。在 OpenVINS 的实现里，视差判据会**覆盖**卡方和最大速度两个门限——如果某个时段特征视差很小（纹理贫乏、或图像看起来「冻结」），就可能注入一次错误的零速更新，与视觉观测打架。

推理看起来很合理，于是改成 `1.0`（两个门限都需通过），当时的判断是「这与 t≈955–975 那种短时大幅的位姿错误特征吻合」。

**然后实测打脸了。** 用轮式真值量同一窗口（t≈286–372s）的路径比：

| 配置 | 路径 / 轮式真值 |
|---|---|
| `zupt_chi2_multipler: 1.0`（我的"修复"） | **0.519** ← 低估运动 2 倍 |
| `zupt_chi2_multipler: 0`（原值） | 0.820 |
| 原始录制（同样是 0） | 1.068 |

**这个改动让 VIO 严重低估运动**，比原来糟糕得多。已还原，并把这段实测数据写进配置文件注释，避免以后重复踩坑。

教训：参数语义的推理再自洽，也要用真值验证；而且「让门限更严格」这种直觉在滤波器里未必成立——ZUPT 被拒绝得太多，运动积分就会失控。

## 8. 工程细节：两个真 bug

这一轮还修了两个我自己写的 bug，都值得记录：

**（1）桥接节点缺 import，静默崩溃**

`vio_odom_bridge.py` 在把 TF 发布改成 `tf2_ros.TransformBroadcaster` 时漏了 `import tf2_ros`。节点在 `__init__` 里抛 `NameError`，0.27 秒内退出——但 `rosnode list` 会短暂显示它，启动日志看起来也正常，**`/odom_world` 一个消息都没有**。

教训：`py_compile` 只查语法，不查名字；「节点起来了」不等于「话题有数据」，必须用 `rostopic hz` 验证。

**（2）定时器回调异常会静默杀死线程**

`rospy.Timer.run()` **不捕获回调异常**。回调里一抛错，定时器线程就死了，而且没有任何日志。已给桥接的定时器体加了 try/except。

## 9. 实时建图逼近真值：`live_mapper` 与「位姿源决定一切」

### 9.1 思路：把离线做法搬到在线

第 6 节确认了离线 `build_map.py` 的结构完整度最好，RTAB-Map 的栅格投影会把墙打碎。两者的差别不在数据，在处理方式：

| `build_map.py` | RTAB-Map 栅格 |
|---|---|
| 按高度分离墙面/地面 | 点云当一整团处理，地面点稀释墙面 |
| 纯命中累积 | 光线投射侵蚀薄墙 |
| 帧抽样（每 5 帧取 1） | 每帧都进 |
| 简单的投影 + 计数 | 八叉树/2D 投影路径 |

于是写了 `live_mapper.py`：**完全照搬 `build_map.py` 的逻辑，但在线运行**——用实时里程计把每帧深度投影到全局系、按高度分类、累积命中，输出 `/map` 和 `/static_map`。

### 9.2 隔离实验：映射器到底行不行？

给 `live_mapper` 加了一个 `~pose_source` 参数：`odom`（实时 VIO）或 `tf`（从 TF 查位姿）。用 `tf` 就能让它跑在**录制下来的原始位姿**上——即和 `build_map.py` 吃完全相同的位姿。

同一 400 秒窗口：

| 配置 | 障碍格 | 自由格 | 结构 |
|---|---|---|---|
| `build_map.py` 离线 | 5,416 | 10,595 | 清晰户型 |
| **`live_mapper` + bag 原始位姿** | **5,589** | **10,535** | **清晰户型，与离线几乎一致** |
| `live_mapper` + 回放 VIO 位姿 | 13,211 | 4,147 | 糊成一团 |

**给定相同位姿，在线映射器几乎完全复现离线地图。** 算法没问题，问题在位姿。

### 9.3 深入分析：为什么回放位姿建不出图

先看整体统计，结论出乎意料：

```
全程路径长度:  轮式真值 79.33m   原始 VIO 89.30m   回放 VIO 78.95m
```

全程看，回放轨迹（78.95m）反而**比原始（89.30m）更接近真值**。抖动也更小（0.586mm vs 0.995mm）。所以问题不在全局统计里。

再看**分段**——这才是关键。把建图窗口按 40 秒切段，计算每段「VIO 路径 / 轮式真值」：

| 窗口 | 原始 VIO | 回放 VIO |
|---|---|---|
| 276–316s | 1.113 | **1.818** |
| 316–356s | 1.064 | 1.168 |
| 356–396s | 1.013 | 1.249 |
| 396–436s | 1.086 | **1.516** |
| 436–476s | 1.078 | **1.748** |
| 476–516s | 1.040 | 1.093 |
| 516–556s | 1.075 | 1.347 |
| 556–596s | 1.083 | 1.232 |
| 596–636s | 1.025 | 1.195 |
| 636–676s | 1.026 | 1.121 |

量化这两组的**稳定性**：

| | 均值 | 标准差 | **变异系数 CV** |
|---|---|---|---|
| 原始 VIO | 1.060 | 0.031 | **0.029** |
| 回放 VIO | 1.349 | 0.246 | **0.182** |

**回放的尺度波动性是原始的 6.3 倍。**

这就是机制所在：

- **恒定的尺度误差** → 地图被整体缩放，墙还是墙，结构连贯；
- **逐段变化的尺度误差** → 相邻时段的点云落在不同位置，同一面墙被画到多个地方 → **涂抹**。

回放的尺度在 1.09 到 1.82 之间摆动，所以墙被打散了。

### 9.4 再往上一层：为什么回放的尺度这么不稳？

答案在 bag 本身。分析深度帧的间隔分布：

```
帧间隔分布 (17121 帧, 平均 17.2 Hz):
  30-45ms  (≈28Hz，相机真实速率)   18.9%
  45-75ms  (≈17Hz)                64.1%
  75-120ms                        14.2%
  >120ms                           0.2%   (最大 194ms)
```

**录制时丢了约 38% 的帧，而且间隔极不规则（34ms 到 194ms）。**

原因不难理解：`rosbag record` 同时写两路 640×480 原始图像（约 25 MB/s）加 333 Hz 的 IMU 和 30 Hz 的 TF，这台虚拟机的磁盘跟不上。

而 VIO 的尺度是**靠视觉观测和 IMU 预积分联合估计**的。图像间隔不规则时，IMU 要在长短不一的间隙里外推，尺度估计的质量随之波动——于是就有了上面那个 CV=0.182。

**所以链条是：**

```
rosbag 丢帧 → 图像间隔不规则 → VIO 尺度逐段波动 → 点云逐段错位 → 地图涂抹
```

而不是「VIO 算法不行」或「映射器有 bug」。

### 9.5 这对实际使用意味着什么

- **实时 Gazebo 会话**（也就是真实用法）：VIO 拿到的是相机全速率的流（约 28 Hz，间隔均匀），尺度稳定性应当接近原始录制那次（CV 0.029），`live_mapper` 就能产出接近真值的地图。**这一点尚未在 Gazebo 里实测。**
- **用 bag 做开发/调试**：回放 VIO 天然比实时差，此时用 `live_mapper` 的 `pose_source:=tf`，直接吃录制下来的位姿。
- **以后录 bag**：这是可以改进的一环——降低录制负担（例如图像降分辨率、或用 `--buffsize`/`-b` 加大缓冲、或录到更快的盘），把丢帧率降下来。

### 9.6 下一步

1. **在 Gazebo 里实测**：全速率 VIO + `live_mapper`，对照真值标注，确认实时地图能否达到离线质量；
2. **改善录制**：把丢帧率从 38% 降下来，让 bag 回放也能代表实时条件；
3. **若实时仍有波动**：再动前端——调研建议的方向包括提高 `num_pts`、调整 `up_msckf_sigma_px`（合成右目有伪影，别过度拒绝匹配）、以及 `init_dyn_mle_max_iter` 开启几轮以改善初始尺度；
4. **闭环导航验证**：等地图稳定后再做。

## 10. 结论与下一步

**这一轮解决了什么：**

- 伪双目吞吐瓶颈（4 倍提速，VIO 不再饿死）；
- 建立并修正了真值基准（轮式里程计积分）；
- 量化了 VIO 的真实精度（0.995 尺度、2 cm RMSE）并定位到两个故障窗口；
- 找到了建图条纹的根因（`Grid/3D` 默认 true 使光线投射失效）并验证修复；
- 实现了 `live_mapper`，并**用隔离实验证明它在给定相同位姿时能复现离线建图的质量**；
- 把「回放建图糊」的根因追到了**录制丢帧**（38%，间隔 34–194ms）导致 VIO 尺度逐段波动（CV 0.182 vs 原始 0.029）；
- 修了两个工程 bug；试了一个 ZUPT「修复」并**用实测否定了它**。

**还没解决的：**

- 实时 Gazebo 下的 `live_mapper` 效果**尚未实测**（这是唯一还没验证的环节）；
- 录制丢帧问题只定位、未解决；
- 全栈负载下伪双目仍会降到 13 Hz；
- 闭环导航（点目标 → 自主行驶）**仍未跑通**。

**下一步优先级：**

1. Gazebo 实测：全速率 VIO + `live_mapper` 对照真值标注；
2. 改善录制（降分辨率 / 加缓冲 / 换盘），让 bag 能代表实时条件；
3. 全栈降负载：`num_pts` 600→300~400、`num_opencv_threads` 4→2~3；
4. 若实时仍有波动，再动前端参数；
4. 最后再验证闭环导航。
