## 1. 纠错一：.161:8082 高层运动服务**没有缺席**（此前 ICMP 判读有误）

- `.161:8082` 的 sport 服务**一直在运行**。它采用 connect() 单客户端语义：
  某客户端建立后，**其他源端口**的 UDP 探测会收到 ICMP port-unreachable ——
  这会被 `udp_port_probe.py` 误读成"端口关闭"。
- 证据：VM 的 `ros_udp highlevel`（自 01:36 起运行）持有该客户端；期间
  - `/proc/net/snmp` Udp InDatagrams ≈ **500/s**（= 对 500Hz 指令流的一问一答）；
  - ros_udp 的 8090 socket Recv-Q 在 0/768/2176 间波动（回包在途）。
  （注：`ros_udp` 已于 2026-10-11 事件后停止，并**保持停止**——SOP 见 §6。）
- `/high_state` 无数据的原因不是服务缺失：**`ros_udp.cpp` 只在 `/high_cmd`
  回调里发布 `/high_state`**（发布语句写在回调内），不发命令就永远看不到状态。
- 触发采样（已实测成功，脚本已留档）：
  ```bash
  rostopic echo -n1 /high_state            # 终端1，先订阅
  python3 ~/VINS-Nav/go1/pub_high_cmd_mirror_once.py   # 终端2
  ```
  该脚本发布的指令与 ros_udp 持续发送的内容逐位相同（mode=0 全零），无行为变化。
  **注意：属"向运动系统发包"，按 SOP 需先打招呼。**

## 2. 纠错二：相机推流端口是 **9000+位置号**，不是 9201–9205

- 板载 SDK 文档（`~/Unitree/sdk/UnitreeCameraSdk/include/StereoCameraCommon.hpp:565-568`）：
  `appsrc ! videoconvert ! omxh264enc ! ... ! rtph264pay ! udpsink host=192.168.123.SEG port=hostPort`，
  **hostPort = 9000 + 相机位置号**（face 相机位置号 1 → **9001**）。
- 实测：face 相机推流在 **VM 192.168.123.101:9001** 实收（RTP v2 pt=96，
  1202 包/10s ≈ 2.4 Mbit/s）；9201–9205 无任何包。
- 接收/解码命令（已产出 PNG 证据，见 §4）：
  ```bash
  python3 ~/VINS-Nav/go1/udp_probe.py --ports 9001 --seconds 10   # 验包
  gst-launch-1.0 -e udpsrc address=192.168.123.101 port=9001 \
    caps="application/x-rtp,media=video,encoding-name=H264" \
    ! rtph264depay ! h264parse ! avdec_h264 ! videoconvert \
    ! videorate ! video/x-raw,framerate=2/1 ! pngenc \
    ! multifilesink location=front_%05d.png
  ```
  （gstreamer1.0-plugins-bad / libav 已装好。）

## 8. "mode 0 空包残留"分析 + 结局与根因（收官）

### 8.1 事实
- 更正后的线索："**mode 0 空包**" = ros_udp 约 36–50 分钟、500Hz 灌入的全零
  HighCmd（mode=0）可能在运动侧留下的残留。
- 服务层判定（主机侧已完成）：ros_udp 死后重探 8082 → 立即回 **1087B**
  （= sizeof(HighState)，即高层状态**未压缩**；低层才是 820B 压缩）→ 服务层
  已自清；残留若有只可能在更深层。
- **我方帧的 CRC 事实**（本地反汇编 amd64 `libunitree_legged_sdk.a` 的
  `UDP::SetSend(HighCmd&)`）：每帧调用 `crc32(cmd, 31)` 写入结构体偏移 0x7d
  再发送 → **发出的 129B 帧带有效 CRC**、内容 mode=0 全零、无任何关节级数据。
  （低层 `SetSend(char*)` 用 `encryptCRC`：XOR 0xedcab9de + byte_swap 混淆——
  将来做低层控制需要，记录备查。）

### 8.2 残留可能驻留的层级（自外向内）
| 层 | 组件 | 证据/现状 | 残留可能 | 清除方式 |
|----|------|-----------|----------|----------|
| 1 | .161:8082 sport 服务会话 | 自清：新探测即回 1087B | 否（排除） | — |
| 2 | 高层指令管线（服务→运动板） | 外部不可见；我方流仅 mode=0 全零、无关节数据 | 理论可能（指令锁存） | 断电 / 重启 Pi 服务 |
| 3 | ukd/桥队列（.161 上 `ukd_triple_udp_node`、`ros2udp_motion_mode_adv` 的 UDP 出口）| 仍在运行（/ros2udp/odom 200Hz 全零持续）；其出流同为"全零内容包"且外部不可见 | 可能（同级全零源） | 断电（全清）/ 重启 .161 服务（次选）|
| 4 | 运动控制板(.10) RAM | 外部不可见 | 可能（队列最终在此消费） | **仅断电** |
| 5 | 电机 Flash 标定 / 固件 | 非易失；电机温度正常（事件前 45–50℃） | 存在但**断电不清** | 电机标定（Unitree 工具/App）/ 维修 |

### 8.3 "断电重上电全清"的成立范围与反例
- **成立**：清空一切**易失**状态（所有进程/队列/RAM：sport 服务、ukd 栈、桥、
  运动板 RAM、网络缓冲）——"队列/空包残留"类假设，断电是超集清除。
- **反例（清不了）**：电机 Flash（零点/方向标定）、固件缺陷、物理硬件。
  若断电后仍异常，直接指向这些层（校准/报修方向）。

### 8.4 结局与根因结论（事件闭环）
- **复测证据（用户执行）**：**断电重上电后，手柄 L2+A 复测左前腿恢复正常**
  （此前纯手柄复测为异常）——预注册判读表"分支 A"命中。
- **根因结论（用户/主机侧认定，本文件照录）**："**mode-0 空包残留**"假说成立——
  本案中 ros_udp 约 36 分钟的全零 HighCmd（mode=0）流在运动侧留下了易失残留，
  为本次左前腿异常的**诱因**；断电清空了该残留。支持证据链：时间窗口吻合
  （流 01:36 起、02:03 数据中 FL 已折叠）、服务层已排除（新探测即回 1087B）、
  纯手柄复测排除按键盘冲突、**断电即愈**。
- 技术注记（如实保留）：外部手段无法做**唯一性**归因（ukd 桥的全零出流属同级
  嫌疑），故按"易失残留类 + 我们的流为诱因"作操作结论记录，并据此制定 SOP（§6）。
- 旁证（事件前数据已可见）：02:03 及 02:0x 的 4 份采样显示**左前腿**（电机槽
  3–5；关节序依 SDK `quadruped.h`：FL_0=3/FL_1=4/FL_2=5）**已处于折叠异常姿态
  且稳定**：
  - 电机 q：FR(−0.375, 1.173, −2.765)｜**FL(1.282, −1.689, −2.803)**｜
    RR(−0.391, 1.204, −2.778)｜RL(0.375, 1.213, −2.767)——FL 大腿偏 ~2.9 rad；
  - 足端位置 footPosition2Body[FL]=(0.192, 0.001, **+0.097**)（其余 y≈±0.15、
    z≈−0.04）→ 左前足收拢抬高 ~14cm。
- 附带效果：断电重启**自动恢复**了三台 Jetson 的相机自启节点（无需手动 restore，
  现状即恢复运行态）；ros_udp 保持停止。
